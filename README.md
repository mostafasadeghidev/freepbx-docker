# FreePBX 17 روی Docker

## اول یک نکته مهم

**سنگوما (Sangoma) هیچ ایمیج داکر رسمی برای FreePBX منتشر نمی‌کند.** بررسی شد
(۱۴۰۵/۰۶/۱۷): در Docker Hub هیچ ایمیجی با نشان Official یا Verified نیست؛ تنها
ایمیج از حساب خودِ `freepbx` یعنی `sng7-tiny` هشت سال است به‌روز نشده و مربوط به
توزیع قدیمیِ SNG7 است. سازمان FreePBX در گیت‌هاب هم هیچ مخزن مربوط به کانتینر
ندارد. بقیه‌ی ایمیج‌ها (daveoxley، jmar71n، flaviostutz و ...) ساخت جامعه‌اند و
بین ۴ تا ۱۰ سال قدمت دارند.

تنها روش نصب رسمی، اجرای `sng_freepbx_debian_install.sh` روی یک **Debian 12
(bookworm)** تمیز است. این پروژه دقیقاً همان را بازتولید می‌کند: یک کانتینر
دبیان ۱۲ با systemd واقعی که همان اسکریپت رسمی را داخل خودش اجرا می‌کند. نسخه‌ی
FreePBX و Asterisk کاملاً رسمی است؛ فقط بستر اجرا کانتینر است.

### ⚠️ `debian:12` را عوض نکنید

اسکریپت رسمی **فقط** bookworm را قبول می‌کند و روی هر چیز دیگری می‌ایستد:

```
Unsupported OS version. This script supports only Debian 12 (bookworm)
```

از آگوست ۲۰۲۵ عمداً به `bookworm` سنجاق شده و حتی جلوی ارتقا به دبیان ۱۳ را با
یک apt preference می‌گیرد. پس `FROM debian:12` در Dockerfile درست است و باید
همان بماند. عوض کردنش به `debian:stable` یا `debian:13` نصب را از کار می‌اندازد.

## این ستاپ برای چه اندازه‌ای است

**حدود ۲۰ داخلی و روزی چند تماس.** این اندازه تنها دلیلی است که این فایل با
دستورالعمل‌های معمولِ FreePBX-in-Docker فرق دارد:

**شبکه‌ی bridge، نه `network_mode: host`.**

آن دستورالعمل‌ها host را لازم دارند چون بازه‌ی پیش‌فرض RTP یعنی ۱۰۰۰۰ تا ۲۰۰۰۰
است — ده هزار پورت UDP که داکر با سرعت معقول منتشرشان نمی‌کند. بیست داخلی ده
هزار پورت لازم ندارد؛ **چهل تا کافی است** (دو پورت برای هر تماس، بیست تماس
همزمان) و چهل پورت بدون مشکل منتشر می‌شود.

در عوض کانتینر فضای شبکه‌ی خودش را نگه می‌دارد، پس **با هیچ‌چیزی که از قبل روی
سرور هست تصادم نمی‌کند** — یعنی اگر روی آن سرور یک وب‌پراکسی (Caddy، Traefik،
nginx) پورت ۸۰ و ۴۴۳ را دارد، هیچ‌چیز لازم نیست جابه‌جا شود.

> اگر ماشین اختصاصی دارید و بازه‌ی کامل RTP را می‌خواهید، فایل
> `compose.host-networking.yml` نسخه‌ی host است:
> `docker compose -f compose.host-networking.yml up -d`

## پیش‌نیازها

- سرور **لینوکسی amd64** (اسکریپت فقط ۶۴ بیتی را قبول می‌کند)
- Docker Engine + Docker Compose v2
- **cgroup v2** روی هاست — این ستاپ systemd را به‌عنوان PID 1 اجرا می‌کند و
  روی هاست با cgroup v1 شکننده می‌شود. بررسی: `stat -fc %T /sys/fs/cgroup`
  باید `cgroup2fs` بدهد.
- حداقل ۲ گیگ رم آزاد (۴ گیگ راحت‌تر) و **۱۵ گیگ** فضای خالیِ دیسک. اندازه‌گیری‌شده
  روی سرورِ تست بعد از نصب: ایمیجِ اسنپ‌شات ۵٫۱ گیگ، `data` ۲٫۱ گیگ و لایهٔ خودِ
  کانتینر حدودِ ۱ گیگ؛ و تا اولین بازسازی از روی اسنپ‌شات، نرم‌افزارِ نصب‌شده دو بار
  روی دیسک است. Coolify روی همان ماشین حدودِ ۳ گیگِ دیگر می‌خواهد.
- پورت‌های ۵۰۶۰ و ۱۰۰۰۰-۱۰۰۳۹ روی هاست آزاد باشند

**توزیع لینوکسِ هاست مهم نیست** — کانتینر دبیان ۱۲ خودش را می‌آورد. چیزی که از
هاست می‌آید هسته، معماری، cgroup و ساعت است.

> **روی Docker Desktop ویندوز یا مک کار نمی‌کند** (systemd + privileged).

## نصبِ سریع — یک فرمان

روی سروری که فقط داکر دارد:

```bash
git clone https://github.com/mostafasadeghidev/freepbx-docker.git
cd freepbx-docker
./setup.sh
```

چند سؤال می‌پرسد که همه‌شان پیش‌فرضِ درست دارند (Enter کافی است)، `.env` و
`pbx.env` را می‌نویسد، و نصب را شروع می‌کند. بعد تا پایانِ نصب پیشرفت را نشان
می‌دهد و سه کارِ باقی‌مانده را که فقط از دستِ آدم برمی‌آید می‌گوید.

`./setup.sh --show` فقط نشان می‌دهد چه می‌نویسد و چیزی را عوض نمی‌کند.
`./setup.sh --yes` هیچ نمی‌پرسد و همهٔ پیش‌فرض‌ها را می‌گیرد.
`./setup.sh --prepare` همه‌چیز را می‌نویسد و پورت‌ها را می‌سنجد، ولی روشن نمی‌کند.

`setup.sh` خودش می‌بیند Coolify روی سرور هست یا نه، و برای تونل می‌پرسد کدام سمت
گوش می‌دهد. در حالتِ «listen» کلیدها، رمز، `server.conf` و `iroute` را **خودش
می‌سازد** و در پایان یک خطِ آماده برای ترمینالِ روتر چاپ می‌کند.

هر سؤال را می‌شود از محیط هم جواب داد — برای برنامه‌ای مثلِ زانا که نصب را بدونِ
کیبورد اجرا می‌کند و نباید به ترتیبِ سؤال‌ها وابسته باشد:

```bash
SETUP_EXTENSIONS=50 SETUP_TUNNEL=listen SETUP_OPERATOR_NET=203.0.113.0/24 ./setup.sh --yes
```

فهرستِ کاملِ متغیرها بالای `setup.sh` است.

**تونل برای نصبی که از قبل کار می‌کند:** `./tunnel/listen.sh --net 203.0.113.0/24`.
همان کاری که `setup.sh` برای تونل می‌کند، روی سیستمی که روشن است: پورت را اول
می‌سنجد، رمزِ روترِ موجود را عوض نمی‌کند، روترِ دوم را با `--user` اضافه می‌کند،
و تا OpenVPN واقعاً گوش ندهد «تمام» نمی‌گوید. نصبی را که هنوز اسنپ‌شات نشده **رد
می‌کند**، چون باز کردنِ پورت کانتینر را از نو می‌سازد.

### ⚠️ بعد از هر تغییر در `.env`: `./apply.sh`، نه `docker compose up`

```bash
./apply.sh            # اول می‌سنجد، بعد اعمال می‌کند
./apply.sh --check    # فقط می‌سنجد
```

دلیلش اندازه‌گیری‌شده است و «یک خطا می‌گیری» نیست. روی ماشینی با Coolify و
`TUNNEL_PORT=443`، کمپوز کانتینرِ تلفن را برای افزودنِ پورت **بازسازی کرد**، نتوانست
کانتینرِ تازه را روشن کند چون Traefik پورتِ ۴۴۳ را داشت، و **هیچ کانتینرِ تلفنی
روشن نماند**. تداخلِ پورت مؤدبانه رد نمی‌شود — سیستم را می‌خواباند.

`apply.sh` قبل از دست زدن به هر چیزی می‌گوید کدام پورت را **چه کسی** گرفته — به
اسم، مثلاً `coolify-proxy`، نه فقط `docker-proxy` — و برای تونل یک پورتِ آزاد
پیشنهاد می‌دهد. همین بررسی در `setup.sh` و `doctor.sh` هم هست.

و یک سؤالِ دوم، که به همان اندازه سیستم را می‌خواباند: **بازسازی نصب را پاک
می‌کند یا نه.** اگر FreePBX فقط داخلِ کانتینرِ در حالِ اجراست و ایمیجی که بازسازی
از آن شروع می‌شود نصب را ندارد، `apply.sh` رد می‌کند و می‌گوید اول اسنپ‌شات. فقط
به `docker diff` نگاه نمی‌کند — درست بعد از `setup.sh` کانتینر هنوز از ایمیجِ ساخت
اجرا می‌شود ولی `.env` اسنپ‌شات را نام می‌برد، و آن بازسازی بی‌خطر است؛ پس داخلِ
خودِ آن ایمیج را هم نگاه می‌کند (بی شبکه، بی pull). آزموده روی سرورِ تست: بازسازی
از اسنپ‌شات انجام شد و `fwconsole` و Asterisk سرِ جایشان بودند.

با کاربرِ غیرِ root (عضوِ گروهِ docker) هم درست کار می‌کند: `ss` نامِ پروسه‌های root
را به او نشان نمی‌دهد، و قبلاً پورت‌های خودِ کیت «گرفته‌شده توسطِ ?» خوانده می‌شدند.

**`setup.sh` روی پوشه‌ای که FreePBX در آن نصب شده اجرا نمی‌شود** — ساختنِ دوبارهٔ
`.env` ایمیج را به ایمیجِ ساخت برمی‌گرداند و نصب را پاک می‌کند. برای تغییر:
`.env` و `./apply.sh`؛ برای تونل: `./tunnel/listen.sh`.

بقیهٔ این فایل همان کار را دستی توضیح می‌دهد، و **تله‌هایی** را که سرِ راه
هست. اگر چیزی خراب شد، جوابش پایین‌تر است.

### اندازه‌گیری‌شده روی یک سرورِ تمیز

همهٔ عددهای این بخش از یک اجرای واقعی آمده، نه از تخمین. ماشین: Ubuntu 26.04
LTS، ۲ هسته، ۳.۸ گیگ رم، ۳۸ گیگ دیسک.

| مرحله | نتیجه |
|---|---|
| سرورِ خام، بدونِ داکر | `setup.sh` با یک جملهٔ روشن رد می‌کند و **هیچ فایلی نمی‌نویسد** |
| نصبِ داکر (اسکریپتِ رسمی) | ۲۹.۸.۰ + کمپوز ۵.۵.۱؛ مخزنِ داکر برای `resolute` موجود است |
| نصبِ FreePBX، تنها روی ماشین | **۲۰ دقیقه** |
| همان نصب، وقتی Coolify هم روی همان دو هسته بود | **۳۰ دقیقه** |
| پورت‌های منتشرشده | ۴۱ پورتِ UDP (۴۰ صدا + SIP)، پنل فقط روی `127.0.0.1` |
| SIP از بیرون | `SIP/2.0 401 Unauthorized` با `Server: FPBX-17.0.33` |
| نصبِ Coolify کنارِ تلفنِ در حال کار | **۲ دقیقه**، بی‌هیچ تصادفِ پورت، کانتینرِ تلفن دست‌نخورده |
| دیسکِ مصرفی در پایان | ۱۳ گیگ (شاملِ Coolify و ایمیجِ اسنپ‌شات) |

### تونل، اندازه‌گیری‌شده از آلمان به یک روترِ ایرانی

آزمونِ واقعی: کانتینرِ FreePBX روی سرورِ هتزنر در نورنبرگ، و یک میکروتیکِ
hAP ax lite LTE6 روی RouterOS 7.25 در ایران.

| | نتیجه |
|---|---|
| جهتِ درست | **سرور گوش می‌دهد، روتر وصل می‌شود** — هر دو خطِ روتر آدرسی از `100.64.0.0/10` داشتند، یعنی NATِ اپراتور و از بیرون غیرقابلِ دسترس |
| احرازِ هویت | نام و رمز، **بدونِ گواهیِ کلاینت** — همان چیزی که `ovpn-client` میکروتیک حرف می‌زند |
| وصل شدن | `authentication succeeded for username` و `internal route 203.0.113.0/24 -> ...` |
| داخلِ کانتینرِ تلفن | `tun0 10.97.0.1/24` و `203.0.113.0/24 via 10.97.0.2` — و روی هاست **صفر** رابطِ tun و صفر مسیر |
| پینگِ اپراتور از تونل | ۰٪ اتلاف، ۱۷۰ms |
| پاسخِ SIPِ اپراتور | `SIP/2.0 603` از `203.0.113.10` — از داخلِ کانتینر، در هر دو حالتِ داکرِ ساده و Coolify |
| پورت | ۱۱۹۴، چون ۴۴۳ روی ماشینِ Coolify دستِ Traefik است |

و تلهٔ `iroute` که یک ساعت وقت گرفت: بدونِ آن روتر فقط ۲۴ بستهٔ keepalive
می‌دید و شمارندهٔ خودش برای شبکهٔ اپراتور تکان نمی‌خورد. شرحش در
`tunnel/README.md`.

**ثبتِ واقعیِ ترانک آزموده نشد** — با همان مشخصاتِ اپراتور، ثبت از سرورِ دوم
ثبتِ سیستمِ اصلی را جابه‌جا می‌کند. آنچه آزموده شد پاسخِ خودِ اپراتور به یک
`REGISTER`ِ بی‌اعتبارنامه است، که مسیر را ثابت می‌کند و چیزی را ثبت نمی‌کند.

**یک تماسِ صوتیِ کامل هم از راهِ این کیت هنوز آزموده نشده.** یک داخلی روی سرورِ
تست ساخته شد و گوشیِ آزمایشی از اینترنت با آن رجیستر کرد؛ ولی کسی با آن زنگ نزد،
پس اینکه صدا از بازهٔ پورت‌های منتشرشده در هر دو جهت رد می‌شود، روی این کیت
اندازه‌گیری نشده است.

### ⚠️ تله‌ای که همین آزمون گرفت

یک `docker compose up -d` برای اعمالِ یک override، کانتینر را بازسازی کرد و
**کلِ نصب را نابود کرد**. بوتِ بعدی همان جملهٔ مستندِ این مخزن را گفت:

```
Failed to start mariadb.service: Unit mariadb.service not found.
```

`fwconsole` نبود، آستریسک نبود، و `./data` هنوز می‌گفت «نصب شده» — پس هیچ‌چیز
دوباره نصب نمی‌شد. راهِ برگشت: پاک کردنِ `data` و نصب از صفر.

این هشدار از روزِ اول در همین فایل بود و **کافی نبود**. پس حالا `setup.sh` خودش
در پایانِ نصب `./snapshot.sh` را اجرا می‌کند و `PBX_IMAGE` را در `.env` به
`freepbx17-official:installed` تغییر می‌دهد. بعد از آن، همان override دوباره
اعمال شد: کانتینر بازسازی شد و `fwconsole`، آستریسک، mariadb و apache همه سرِ
جایشان ماندند. `doctor.sh` هم اگر این وضعیت برنگشته باشد **قرمز** می‌دهد، نه زرد.

### چند داخلی؟

تنها چیزی که با اندازه عوض می‌شود، تعدادِ پورتِ صداست. `setup.sh` خودش حساب
می‌کند؛ این جدول برای وقتی است که دستی می‌نویسی:

| داخلی | `RTP_END` | تماسِ هم‌زمان |
|---|---|---|
| تا ۲۰ | `10039` | ۲۰ |
| تا ۵۰ | `10099` | ۵۰ |
| تا ۱۰۰ | `10199` | ۱۰۰ |

هر چه اینجا می‌گذاری باید **در خودِ FreePBX هم** همان باشد:
`Settings → Asterisk SIP Settings → RTP Port Ranges`. اگر این دو یکی نباشند،
تماس‌هایی که پورتشان بیرونِ اشتراک بیفتد صدا را یک‌طرفه می‌شنوند.
`./doctor.sh` این را می‌سنجد.

پیش‌فرضِ خودِ FreePBX ۱۰۰۰۰ تا ۲۰۰۰۰ است — ده هزار پورت، که داکر با سرعتِ
معقول منتشرشان نمی‌کند. بیشترِ دستورالعمل‌های FreePBX روی داکر برای همین به
`network_mode: host` پناه می‌برند و بعد با هر چیزِ دیگری روی آن ماشین تصادف
می‌کنند. این ستاپ آن راه را نرفته.

### وقتی چیزی کار نمی‌کند

```bash
./doctor.sh
```

هر چیزی که می‌سنجد یک بار روی یک نصبِ واقعی خراب شده بود: DNSِ داخلِ کانتینر،
آدرسِ عمومیِ آستریسک، هم‌خوانیِ بازهٔ پورتِ صدا، ماژولِ فایروال، و اینکه ترانک
ثبت شده یا نه. چیزی را عوض نمی‌کند؛ فقط می‌گوید چه دید.

### روی سروری که Coolify دارد

آزموده شد روی Ubuntu 26.04 با Coolify نصب‌شده **کنارِ** همین کیت. سه چیز
اندازه‌گیری شد:

**۱. تصادفی نیست.** Coolify پورت‌های ۸۰، ۴۴۳ (و ۴۴۳/udp برای HTTP/3) و ۸۰۸۰ را
می‌گیرد و خودش روی ۸۰۰۰ می‌نشیند. تلفن ۵۰۶۰ و بازهٔ RTP را دارد و پنل روی
`127.0.0.1:8088`. نصبِ Coolify روی ماشینی که تلفن رویش کار می‌کرد، **دو دقیقه**
طول کشید و کانتینرِ تلفن دست نخورد.

**۲. «پنل را روی ۱۲۷.۰.۰.۱ بگذار و Coolify را به آن وصل کن» کار نمی‌کند.**
این حرفِ بدیهی است و غلط. اندازه‌گیری از داخلِ پراکسیِ خودِ Coolify:

```
wget http://10.0.0.1:8088/   → Connection refused
wget http://freepbx:80/      → bad address 'freepbx'
```

پراکسی داخلِ یک کانتینر است؛ به پورتی که روی **لوکال‌هاستِ هاست** بسته شده
نمی‌رسد، و کانتینری را که روی شبکهٔ دیگری است با اسم پیدا نمی‌کند.

**۳. راهِ درست همان است که Caddy روی سرورِ نویسنده دارد:** کانتینر را به شبکهٔ
پراکسی وصل کن. برای همین `compose.coolify.yml` هست — **بعد از ساختنِ حسابِ مدیر**
(«ترتیبِ امنِ اولین ورود»)، در `.env`:

```
PANEL_DOMAIN=pbx.example.com
COMPOSE_FILE=compose.yml:compose.coolify.yml
```

و `./apply.sh`. در `.env`، نه با `-f` در خطِ فرمان: وگرنه `up -d`ِ بعدی، از هر کس
یا هر ابزاری، فایلِ Coolify را جا می‌اندازد و پنل از پراکسی می‌افتد.

پنل را به شبکهٔ `coolify` می‌آورد و با برچسب‌های Traefik روی آن دامنه با
گواهیِ Let's Encrypt منتشر می‌کند. صدا از پراکسی رد نمی‌شود و لازم هم نیست —
پورت‌هایش مستقیم منتشرند.

و آن را **از ترمینال** اجرا کن، نه از داخلِ پنلِ Coolify: Coolify فایلِ compose
را بازنویسی و خودش نام‌گذاری می‌کند، و آن‌وقت این پوشه دیگر مالِ تو نیست.

> ⚠️ روی سرورِ Coolify تونل را روی ۴۴۳ نگذار. آنجا ۴۴۳ دستِ Traefik است و
> چیزی برای `port-share` باقی نمی‌ماند.

### تونل، اگر لازم بود

فقط برای سروری که خارج است و اپراتورش آدرسِ داخلِ کشور می‌خواهد. دو جهت دارد، و
جهتِ درست به **سمتِ داخلِ کشور** بستگی دارد، نه به سرور:

- **سرور گوش می‌دهد، روتر وصل می‌شود — تقریباً همیشه همین.** روترِ یک خطِ اداره
  یا سیم‌کارت پشتِ NATِ اپراتور است و هیچ‌کس نمی‌تواند به آن وصل شود
  (اندازه‌گیری‌شده: هر دو خطِ روتر آدرسی از `100.64.0.0/10` داشتند). در `setup.sh`
  جوابِ سؤالِ تونل را `listen` بده، یا روی نصبی که کار می‌کند:
  `./tunnel/listen.sh --net <شبکهٔ اپراتور>`.
- **سرور زنگ می‌زند** — فقط وقتی سمتِ مقابل آدرسِ عمومی دارد و یک فایلِ `.ovpn`
  به تو داده: فایل در `tunnel/client.ovpn`، `COMPOSE_PROFILES=tunnel` در `.env`،
  و `./apply.sh`.

شرحِ کامل در `tunnel/README.md`.

## نصبِ دستی


پوشه را روی سرور بگذارید (گیت یا `scp`).

**اول فایل‌های تنظیمات را بسازید** — هیچ‌کدام در گیت نیستند، فقط الگوهایشان:

```bash
cp .env.example .env
cp pbx.env.example pbx.env
```

`.env` اندازه و پورت‌ها و ایمیج را نگه می‌دارد و `pbx.env` تنظیماتِ نصب‌کننده را.
در صورت نیاز `TZ` و `INSTALL_ARGS` را در `pbx.env` ویرایش کنید، بعد:

```bash
docker compose up -d
```

بار اول ایمیج ساخته می‌شود (۵–۱۰ دقیقه)، بعد کانتینر بالا می‌آید و **داخل
خودش** اسکریپت رسمی را اجرا می‌کند — این مرحله **۲۰ تا ۴۰ دقیقه** طول می‌کشد.

```bash
docker compose logs -f freepbx
```

دنبال این خط بگردید:

```
[bootstrap] FreePBX installation finished.
```

لاگ کامل خود اسکریپت:

```bash
docker compose exec freepbx bash -c 'tail -f /var/log/pbx/freepbx17-install-*.log'
```

### ⚠️ `--opensourceonly` نصب را می‌شکند

اندازه‌گیری شد روی نصب‌کنندهٔ نسخهٔ ۱.۱۵ (۱۴۰۵/۰۶/۱۷). این فلگ ماژول‌های
تجاری را نصب **نمی‌کند** و بعد تلاش می‌کند همان‌ها را حذف کند:

```
xargs -t -I {} fwconsole ma -f remove {}
Error at line: 1293 exiting with code 123
```

`xargs` وقتی هر فراخوانی‌اش شکست بخورد کد ۱۲۳ می‌دهد و `set -e` اسکریپت را
همان‌جا می‌کشد — **بعد از اینکه همه‌چیز نصب شده و کار می‌کند**. در لاگ ۱۱۶ بار
«نصب نیست» آمده بود.

`INSTALL_ARGS` را خالی بگذارید. ماژول‌های تجاری نصب می‌شوند ولی بدون لایسنس
کاری نمی‌کنند؛ هزینه‌شان دیسک است نه رفتار.

### نصب هر بار از اینترنت می‌آید

نصب‌کنندهٔ رسمی هر بار تازه از گیت‌هاب گرفته می‌شود (شاخهٔ `master`)، و خودش
بسته‌ها را از مخزن‌های دبیان و FreePBX می‌کشد. پس:

- **دو نصب در دو ماه لزوماً یکسان نیستند.** برای یکسان بودن، نسخه را سنجاق کن:
  خطِ `INSTALLER_URL` در `pbx.env` را باز کن و `master` را با شناسهٔ یک commitِ
  مشخص عوض کن.
- **سرور باید به گیت‌هاب و آن مخزن‌ها برسد.** از داخلِ ایران ممکن است نرسد؛ این کیت
  روی سرورهایی در آلمان نصب و آزموده شده است.

بعد از نصب، اسنپ‌شات همان نسخهٔ ثابت است: با «پشتیبانِ کامل» (پایین‌تر) همان را
به سرورِ دیگر می‌بری، بی‌آنکه دوباره از اینترنت نصب شود — مسیرِ برگرداندن روی سرورِ
تست تمرین شده است.

### دو چیز دیگر که سرِ نصب واقعی پیش آمد

**لاگ در `docker compose logs` نیست.** با systemd به‌عنوان PID 1، خروجی به
ژورنالِ داخل کانتینر می‌رود. لاگ واقعی این‌جاست:

```bash
docker exec freepbx tail -f /var/log/pbx/freepbx17-install-*.log
```

**بعد از نصب، صفحهٔ پیش‌فرض دبیان را می‌بینید نه فری‌پی‌بی‌ایکس.** بستهٔ
apache2 فایل `index.html` خودش را در ریشهٔ وب می‌گذارد و Apache آن را
**قبل از** `index.php` فری‌پی‌بی‌ایکس سرو می‌کند:

```
DirectoryIndex index.html index.cgi index.pl index.php ...
```

کنارش بگذارید:

```bash
docker exec freepbx mv /var/www/html/index.html /var/www/html/index.html.debian-default
```

**حین نصب رم هاست را بپایید.** این پرریسک‌ترین لحظه است؛ اگر رم تمام شود کرنل
یک پروسه را می‌کشد و ممکن است چیز دیگری روی همان سرور باشد.

## ⚠️ بلافاصله بعد از نصب: عکس بگیرید

**ولوم‌ها داده را نگه می‌دارند، نرم‌افزار را نه.**

نصب‌کننده mariadb، apache، php، asterisk و یونیت‌های systemd آن‌ها را داخل
**سیستم‌فایل خودِ کانتینر** می‌نویسد. آن سیستم‌فایل هر بار که
`docker compose up` کانتینر را بازسازی کند از روی ایمیج از نو ساخته می‌شود —
و کل نصب می‌رود. فشردن دکمهٔ «بروزرسانی» در یک رابط کافی است.

چیزی که می‌ماند از یک شروع تمیز هم بدتر است: `./data` هنوز نشانهٔ «نصب شده»
را دارد، پس `bootstrap.sh` نصب را رد می‌کند و سرویس‌هایی را استارت می‌کند که
دیگر وجود ندارند:

```
Failed to start mariadb.service: Unit mariadb.service not found.
```

اندازه‌گیری شد روی یک نصب واقعی. جبرانش یک نصب بیست‌دقیقه‌ای دیگر بود.

### ⚠️ و نصب دوباره روی دادهٔ قبلی نمی‌نشیند

اگر این اتفاق افتاد، وسوسه می‌شوی نشانه را برداری و بگذاری نصب‌کننده دوباره
اجرا شود. **کار نمی‌کند.** اندازه‌گیری شد: بستهٔ `freepbx17` نصب می‌شود ولی
`/usr/sbin/fwconsole` ساخته نمی‌شود، چون `/var/www/html` از نصب قبلی پر است و
بسته آن را «قبلاً نصب‌شده» می‌بیند و آن مرحله را رد می‌کند. نتیجه:

```
line 1304: fwconsole: command not found
```

اگر به این حالت رسیدی، تنها راه تمیز این است: از `./data` پشتیبان بگیر،
`docker compose down` بزن، کل `./data` را پاک کن، و یک نصب تمیز شروع کن. بعد
**بلافاصله** `./snapshot.sh`.

**علاجش یک بار اجرای این است** — `setup.sh` خودش انجامش می‌دهد؛ این برای نصبِ
دستی است:

```bash
./snapshot.sh
```

کانتینرِ نصب‌شده را به ایمیج `freepbx17-official:installed` تبدیل می‌کند. بعد
**یک خط در `.env`**:

```
PBX_IMAGE=freepbx17-official:installed
```

`compose.yml` ویرایش نمی‌شود و بخشِ `build:` آن **سرِ جایش می‌ماند**. از آن به بعد
بازسازی از حالتِ نصب‌شده شروع می‌شود، چند ثانیه طول می‌کشد، و چیزی از دست
نمی‌رود.

### ⚠️ بعد از نصب هرگز: `docker compose build` یا `up -d --build`

کمپوز فقط وقتی می‌سازد که ایمیجی که `PBX_IMAGE` نام می‌برد وجود نداشته باشد — و
بعد از نصب، این دقیقاً لحظهٔ خطرناک است. این دو فرمان یک ایمیجِ **تازه و خالی**
می‌سازند و اسمِ اسنپ‌شات را رویش می‌گذارند؛ بازسازیِ بعدی نصب را پاک می‌کند.
اندازه‌گیری‌شده با کانتینرهای آزمایشیِ هم‌شکلِ همین کیت، روی داکر ۲۹: بعد از
`docker compose build` و یک `up -d`، `fwconsole` دیگر نبود. همین اتفاق وقتی هم
می‌افتد که یک پاک‌سازیِ خودکارِ ایمیج اسنپ‌شات را پاک کند — پاک‌سازیِ دوره‌ایِ
Coolify روی سرورِ تست همین کار را کرد.

`./apply.sh` پیش از هر بازسازی می‌بیند ایمیجی که بازسازی از آن شروع می‌شود واقعاً
FreePBX دارد یا نه، و اگر ندارد رد می‌کند؛ `./doctor.sh` هم همین را قرمز نشان
می‌دهد. اگر پیش آمد، کانتینرِ روشن هنوز نصب را دارد: `./snapshot.sh` را دوباره
بزن تا اسمِ اسنپ‌شات باز به نصب اشاره کند.

> بعد از هر چیزی که **نرم‌افزار** را عوض کند — `fwconsole ma upgradeall`،
> ارتقای بسته‌های دبیان، نصب ماژول — دوباره `./snapshot.sh` را بزنید.
> برای تغییرِ **داده** (داخلی جدید، تنظیمات) لازم نیست؛ آن‌ها در ولوم‌اند.

## بعد از نصب: مهم‌ترین کار — ترتیبِ امنِ اولین ورود

FreePBX تا وقتی کسی پنل را باز نکرده **هیچ مدیری ندارد**، و اولین کسی که بازش
کند مدیر می‌شود — بی‌دعوت‌نامه و بی‌هیچ بررسی‌ای. پس ترتیب این است:

۱. **نصب**، با پنل فقط روی خودِ سرور (`PANEL_BIND=127.0.0.1`، پیش‌فرض). روی سرورِ
   Coolify به سؤالِ دامنه در `setup.sh` جواب نده و خالی بگذار.

۲. **ساختنِ مدیر**، از راهِ یک تونلِ SSH — پنل از هیچ جای دیگری دیده نمی‌شود:

   ```bash
   ssh -L 8088:127.0.0.1:8088 root@<سرور>
   ```

   بعد در مرورگر `http://127.0.0.1:8088`. (زانا همین در را از صفحهٔ تلفن باز
   می‌کند: «پنل را باز کن».)

۳. **بعد از آن**، اگر دامنه می‌خواهی، منتشرش کن. روی Coolify در `.env`:

   ```
   PANEL_DOMAIN=pbx.example.com
   COMPOSE_FILE=compose.yml:compose.coolify.yml
   ```

   (با تونل: `compose.yml:compose.coolify.yml:compose.tunnel-server.yml`) و بعد
   `./apply.sh`. با Caddy یا nginxی که مستقیم روی خودِ سرور نصب است، بخشِ «پنل با
   دامنه و HTTPS» پایین‌تر.

اگر دامنه را همان اول بدهی، پنل از همان لحظه روی اینترنت است؛ `setup.sh` در پایان
همین را می‌گوید، و مدیر را **همان لحظه** بساز. روی سرورِ تستِ همین کیت این حالت
واقعاً پیش آمد: پنل روی یک دامنهٔ عمومی با گواهیِ معتبر، و صفر حسابِ مدیر.

### تله‌ی اصلی — NAT

با شبکه‌ی bridge، Asterisk فکر می‌کند آدرسش `172.x.x.x` است و همان را داخل
پیام‌های SIP می‌نویسد. گوشی صدا را به آدرسی می‌فرستد که از بیرون وجود ندارد.

**نشانه: تماس وصل می‌شود، زنگ می‌خورد، جواب می‌دهید، و یک طرف هیچ نمی‌شنود.**

**`setup.sh` دو تا از این‌ها را خودش درست می‌کند** — آدرسِ عمومی و بازهٔ RTP — با
`./nat.sh`، از راهِ ماژولِ تنظیماتِ SIPِ خودِ FreePBX و یک reload، و بعد از خودِ
Asterisk می‌خواند که واقعاً رسیده. روی یک نصبِ تازهٔ همین کیت اندازه‌گیری‌شده:
FreePBX با `10000-20000` و بدونِ آدرسِ عمومی نصب می‌شود؛ بعد از `nat.sh`،
Asterisk گفت `Port start: 10000 / Port end: 10039` و آدرس روی transport نشست.

```bash
./nat.sh --check                 # الان Asterisk چه دارد
./nat.sh                         # درستش کن (آدرس را از اینترنت می‌پرسد)
./nat.sh --address 203.0.113.7   # با آدرسی که خودت می‌دهی
```

`nat.sh` آدرسِ عمومی را **یک بار** می‌پرسد و ثابت می‌نویسد. اگر IPِ سرور عوض شد —
انتقال به سرورِ دیگر، یا IPی که ثابت نیست — `./nat.sh` را دوباره بزن؛ وگرنه
آستریسک صدا را به آدرسِ قدیمی می‌فرستد.

Local Networks و آدرسِ رسانهٔ ترانکی که از تونل می‌رود را **نمی‌زند** — آن‌ها به
ترانک بستگی دارند. دستی، در `Settings → Asterisk SIP Settings`:

| تنظیم | مقدار |
|---|---|
| External Address | IP عمومی سرور |
| Local Networks | زیرشبکه‌ی داکرِ این کانتینر |
| RTP Port Ranges | `10000` تا `10039` |

سومی باید **دقیقاً** با `ports:` در `compose.yml` یکی باشد. اگر Asterisk پورتی
بیرون این بازه انتخاب کند، آن پورت منتشر نشده و صدا نمی‌رسد.

زیرشبکه‌ی داکر را اینطور بگیرید:

```bash
docker inspect freepbx --format '{{range .NetworkSettings.Networks}}{{.Gateway}}{{end}}'
```

### پنل با دامنه و HTTPS

**اول مدیر را بساز** (بخشِ بالا). بعد، اگر Caddy یا nginx **مستقیم روی خودِ سرور**
نصب است، آن را به `127.0.0.1:8088` وصل کن — با Caddy یک بلوکِ ساده کافی است و
گواهی خودکار گرفته می‌شود. **روی Coolify این راه کار نمی‌کند**، چون پراکسی‌اش داخلِ
یک کانتینر است و به لوکال‌هاستِ سرور نمی‌رسد (اندازه‌گیری‌شده، بخشِ Coolify)؛ آنجا
`compose.coolify.yml` است.

## پورت‌ها

| پورت | کاربرد | کجا منتشر می‌شود |
|---|---|---|
| `5060/udp`, `5060/tcp` | SIP | روی همه‌ی رابط‌ها |
| `10000-10039/udp` | RTP (صدا) | روی همه‌ی رابط‌ها |
| `8088/tcp` | پنل وب | **فقط `127.0.0.1`** |
| `5061/tcp` | SIP over TLS | در compose کامنت است |

⚠️ **به‌محض باز شدن ۵۰۶۰، اسکنرها ظرف چند ساعت پیدایش می‌کنند.** هدفشان
خرابکاری نیست، تماس بین‌الملل مجانی است — قبضش را شما می‌دهید.

- رمزِ هر داخلی را **بلند و تصادفی** بگذارید، نه `1234`.
- **fail2ban داخلِ کانتینر** روشن است و تلاش‌های پیاپیِ ورود با رمزِ غلط را
  می‌بندد. ماژولِ **Firewall**ِ خودِ FreePBX را در این کانتینر **روشن نکنید**:
  DNS را می‌شکند و گوشیِ سالم را می‌بندد — شرحش در بخشِ «ماژول فایروالِ FreePBX
  در کانتینر خاموش است».
- اگر گوشی‌ها آدرسِ ثابت دارند، ۵۰۶۰ را به همان‌ها محدود کنید — در **فایروالِ
  شرکتِ سرور** (مثلاً Cloud Firewallِ هتزنر)، نه با `ufw`: پورتی که داکر منتشر کرده
  پیش از قواعدِ `ufw` رسیدگی می‌شود و `ufw` رویش اثری ندارد.
- اگر شرکتِ سرور جلوی ماشین فایروال دارد، ۵۰۶۰ و **کلِ بازهٔ صدا** (UDP) باید آنجا
  هم باز باشند؛ وگرنه نتیجه همان صدای یک‌طرفه است.

یکی‌یکی از فرمِ پنل. برای چندتا فقط `bulkimport` — نه API و نه دست بردن در
دیتابیس: `addDevice` و `addUser` حدودِ ۳۵ کلید را مستقیم می‌خوانند و سرِ اولین
کلیدِ نبوده می‌میرند، و رکوردِ نیمه‌ساخته بعد از آن `fwconsole reload` را کلاً از کار
می‌اندازد (اندازه‌گیری‌شده، `Undefined array key "account"`).

```bash
cat > ext.csv <<'EOF'
extension,name,description,tech,secret
101,Reception,,pjsip,<رمزِ-بلند-و-تصادفی>
102,Office,,pjsip,<رمزِ-بلند-و-تصادفی>
EOF
docker cp ext.csv freepbx:/tmp/ext.csv && rm ext.csv
docker compose exec -T freepbx fwconsole bulkimport --type=extensions /tmp/ext.csv --replace
docker compose exec -T freepbx fwconsole reload
docker compose exec -T freepbx rm /tmp/ext.csv
```

دو چیز که هرکدام یک بار وقت گرفت: `--replace` حتی وقتی چیزی برای جایگزینی نیست
**لازم است** — بدونش `bulkimport` کار را تمام نمی‌کند. و بدونِ `fwconsole reload`
داخلی‌ها در دیتابیس هستند ولی آستریسک هنوز نمی‌شناسدشان: `pjsip show endpoints`
هیچ نشان نمی‌دهد.

## دیتا کجاست

همه چیز در `./data/` کنار همین فایل:

| مسیر | محتوا |
|---|---|
| `data/mysql` | دیتابیس MariaDB |
| `data/etc-asterisk` | کانفیگ Asterisk |
| `data/lib-asterisk` | ساندفایل‌ها، ماژول‌ها |
| `data/spool-asterisk` | ویس‌میل، ضبط مکالمات، صف‌ها |
| `data/www` | پنل وب |
| `data/log-asterisk`, `data/log-pbx` | لاگ‌ها |
| `data/persist` | `freepbx.conf`، `odbc.ini` و فایل نشانه‌ی «نصب انجام شد» |

پوشه‌های `data/` را خود داکر موقع اولین اجرا می‌سازد؛ لازم نیست منتقل شوند.

برای نصب از صفر: `docker compose down`، کلِ `./data/` را پاک کن، ایمیجِ اسنپ‌شات را
هم (`docker image rm freepbx17-official:installed`)، و بعد `./setup.sh`. فقط برداشتنِ
نشانهٔ `data/persist/.freepbx-installed` کافی **نیست** — نصب روی دادهٔ قبلی
نمی‌نشیند (بخشِ «و نصب دوباره روی دادهٔ قبلی نمی‌نشیند»).

### پشتیبانِ کامل: سه تکه، نه یکی

`./data` به‌تنهایی پشتیبان نیست. نرم‌افزار داخلِ آن نیست — داخلِ ایمیجِ اسنپ‌شات
است — و `./data` به‌تنهایی روی سرورِ تازه همان تلهٔ «نشانهٔ نصب هست ولی نرم‌افزار
نیست» را می‌سازد. پشتیبانِ کامل این‌هاست: ایمیج، پوشهٔ داده با فایل‌های تنظیمات،
و رمزهای تونل اگر تونل داری. در پوشهٔ کیت، به‌عنوانِ root:

```bash
docker save freepbx17-official:installed | gzip > ../freepbx-image.tgz   # تلفن روشن می‌ماند
docker compose stop                                                        # از اینجا تماس‌ها قطع‌اند
tar czf ../freepbx-files.tgz data .env pbx.env \
    $(ls -d tunnel/users tunnel/server.conf tunnel/ccd tunnel/pki tunnel/client.ovpn 2>/dev/null)
docker compose start
```

`freepbx-files.tgz` رمز و کلید دارد — `.env` و `pbx.env`، رمزِ دیتابیس در `data`،
کلیدهای تونل — پس آن را مثلِ رمز نگه دار. و هر دو فایل را **جایی بیرون از همین
سرور**: پشتیبانی که روی همان دیسک است با همان دیسک از بین می‌رود.

برگرداندن، روی سروری که فقط داکر دارد:

```bash
git clone https://github.com/mostafasadeghidev/freepbx-docker.git
cd freepbx-docker
tar xzf ../freepbx-files.tgz
gunzip -c ../freepbx-image.tgz | docker load
./apply.sh
./nat.sh              # آدرسِ عمومیِ سرورِ تازه
```

اگر سرور عوض شده: روی روتر `connect-to` تونل را به آدرسِ تازه بده، و اگر پنل روی
دامنه است DNSِ آن را. روی سروری که Coolify ندارد، `compose.coolify.yml` را از
`COMPOSE_FILE` در `.env` بردار.

**تمرین‌شده روی سرورِ تست (۱۴۰۵/۰۷/۰۴):** پشتیبان گرفته شد، پوشه و ایمیج هر دو
پاک شدند، و همه‌چیز فقط از روی این دو فایل برگشت — حسابِ مدیر، داخلی‌ها، تونل،
پنل و دامنه — با `doctor.sh` بی‌هیچ خرابی.

| | زمان | اندازه |
|---|---|---|
| ذخیرهٔ ایمیج (تلفن روشن) | ۱۳۹ ثانیه | ۱٫۷۵ گیگ |
| خاموش، آرشیوِ فایل‌ها، روشن | ۱۶۲ ثانیه قطعی | ۱٫۱۹ گیگ |
| برگرداندن: فایل‌ها، بارگذاریِ ایمیج، `apply.sh` | ۱۲۸ ثانیه | — |

آنچه فقط در لایهٔ خودِ کانتینر است — فریم‌ورِ گوشی‌هایی که FreePBX بعداً دانلود
می‌کند (روی سرورِ تست حدودِ ۱ گیگ) و لاگ‌ها — در پشتیبان نیست و لازم هم نیست؛
دوباره ساخته می‌شود.

## چه چیزی منتقل شود

**همهٔ این پوشه، با `git clone`** — نه تکه‌ای از آن. اسکریپت‌ها به هم تکیه دارند
(`apply.sh`، `doctor.sh` و `setup.sh` از `scripts/` می‌خوانند)، و `resolv.conf` روی
کانتینر سوار می‌شود: اگر نباشد، داکر جایش یک **پوشه** می‌سازد و کانتینر اصلاً بالا
نمی‌آید (اندازه‌گیری‌شده: `Are you trying to mount a directory onto a file`). فهرستی
که قبلاً اینجا بود همین فایل را نداشت.

`git clone` یک کارِ دیگر هم می‌کند که کپیِ دستی نمی‌کند: اسکریپت‌ها اجرایی می‌مانند.
`.env` و `pbx.env` را `setup.sh` می‌سازد، و `data/` را داکر.

### این مخزن برای عمومی شدن امن است

`.gitignore` طوری نوشته شده که هیچ‌چیز حساسی وارد گیت نشود:

| چه چیزی | چرا |
|---|---|
| `pbx.env` | فایل تنظیمات واقعی — امروز خالی از راز است، فردا شاید نه |
| `data/` | دیتابیس MariaDB با رمزی که نصب‌کننده می‌سازد، کانفیگ Asterisk، ویس‌میل و **ضبط مکالمات** |
| `*.log` | لاگ‌ها کانفیگ را نقل می‌کنند و گاهی رمز را با آن |

هیچ IP، دامنه، ایمیل یا کلیدی در فایل‌های این مخزن نیست — بررسی شد.

## تلهٔ DNS: کانتینر نام‌ها را حل نمی‌کند

اندازه‌گیری‌شده روی همین سرور. کانتینر FreePBX تنها کانتینری بود که هیچ نامی
را حل نمی‌کرد؛ بقیهٔ کانتینرهای همان هاست بی‌مشکل کار می‌کردند.

علتش این است: داکر یک DNS داخلی روی `127.0.0.11` می‌گذارد که فقط با یک قاعدهٔ
NAT داخل network namespace خودِ کانتینر کار می‌کند. این کانتینر `privileged`
است و ماژول فایروال FreePBX به‌همراه fail2ban کل جدول iptables را بازنویسی
می‌کنند — و همان قاعده را پاک می‌کنند:

```
$ docker exec freepbx iptables -t nat -S | grep 127.0.0.11
(هیچی)
```

نتیجه در عمل بدتر از چیزی است که به نظر می‌رسد: PBX‌ای که DNS ندارد نه
می‌تواند ماژول به‌روز کند، نه می‌تواند نام میزبان ترانک SIP را حل کند. یعنی
تماس خروجی بی‌صدا از کار می‌افتد.

### ⚠️ `dns:` این را حل نمی‌کند — آزموده شد

اولین راه‌حل یک `dns:` صریح در `compose.yml` بود، با این تصور که ریزالورِ
داخلیِ داکر را دور می‌زند. **دور نمی‌زند.** داکر همچنان
`nameserver 127.0.0.11` را در resolv.conf می‌نویسد و آن فهرست را فقط
به‌عنوان upstreamِ همان ریزالور به کار می‌برد:

```
nameserver 127.0.0.11
# ExtServers: [185.12.64.1 185.12.64.2 1.1.1.1]
```

یعنی کانتینر همچنان به ریزالورِ داخلی و به همان قاعدهٔ NAT وابسته می‌ماند.

### اندازه‌گیری، که علت را جای دیگری نشان داد

از داخلِ همان کانتینر، سه پرسشِ DNS خام:

```
127.0.0.11   (ریزالورِ داکر)  →  TimeoutError
1.1.1.1                       →  answered
185.12.64.1                   →  answered
```

پس شبکه سالم است و **خودِ ریزالورِ داخلی جواب نمی‌دهد**. این حتی بعد از
خاموش کردنِ ماژول فایروال و بازسازیِ کانتینر هم ادامه داشت — قاعده‌های NAT
سرِ جایشان برگشتند و ریزالور باز هم تایم‌اوت داد.

### راه‌حلی که کار می‌کند

فایلِ `resolv.conf` مخزن، read-only روی فایلِ کانتینر سوار می‌شود:

```yaml
    volumes:
      - ./resolv.conf:/etc/resolv.conf:ro
```

این ری‌استارت و بازسازی هر دو را دوام می‌آورد، چون بایند مانت است نه چیزی که
داکر بازنویسی‌اش کند.

**هزینه‌اش:** کانتینر دیگر نمی‌تواند کانتینرهای دیگر را با نام حل کند. اینجا
چیزی به آن نیاز ندارد — mariadb و apache و asterisk همه داخلِ همین یک
کانتینرند. پراکسیِ جلویی هم این کانتینر را از سمتِ **خودش** حل می‌کند که
دست‌نخورده است.

اگر کانتینر همین حالا بالاست و نمی‌خواهید بازسازی‌اش کنید، موقتاً (این با
هر بار روشن شدنِ کانتینر از بین می‌رود — بایند مانتِ بالا نمی‌رود):

```bash
docker exec freepbx bash -c 'printf "nameserver 1.1.1.1\n" > /etc/resolv.conf'
```

### ⚠️ ولی `dns:` فقط روی کانتینری اثر دارد که با آن **ساخته** شده باشد

این تله یک بار یک ساعت گرفت. `docker restart` و ری‌استارتِ خودِ سرور هر دو
کانتینر را با تنظیماتِ **موجودِ خودش** بالا می‌آورند و اصلاً `compose.yml` را
نمی‌خوانند. پس کانتینری که قبل از اضافه شدنِ این خط ساخته شده همچنان DNS خرابِ
خودش را دارد، و آدم فکر می‌کند اصلاحیه کار نکرده.

```bash
./apply.sh                 # بازسازی می‌کند، پس از سنجیدنِ اینکه نصب می‌ماند — همین لازم است
docker restart freepbx     # این نه
```

### نشانه‌اش از خودِ خرابی دورتر است

DNS که خراب باشد، آستریسک نامِ ترانک را حل نمی‌کند و **هیچ بستهٔ SIPی
نمی‌فرستد**. ولی یک پروبِ دستی با آی‌پی از همان کانتینر `200 OK` می‌گیرد. آن
تضاد — «مسیر سالم است ولی ثبت نمی‌شود» — امضای همین مشکل است:

```bash
docker exec freepbx getent hosts voip.example.ir   # خالی = همین
tcpdump -ni tun0                                   # هیچ بسته‌ای از آستریسک
```

و چون آستریسک نام را فقط موقعِ بالا آمدن حل می‌کند، بعد از درست کردنِ DNS
حتماً `fwconsole restart` لازم است — وگرنه اشیای ثبت اصلاً ساخته نمی‌شوند.

از این نسخه به بعد `healthcheck` در `compose.yml` همین را می‌پرسد: کانتینری که
نام حل نمی‌کند `unhealthy` نشان داده می‌شود، به‌جای اینکه ساعت‌ها بعد به‌شکلِ
«تلفن‌ها ثبت نمی‌شوند» بروز کند.

## ماژول فایروالِ FreePBX در کانتینر خاموش است

`PBX_FIREWALL=off` پیش‌فرض است و `bootstrap.sh` سرِ **هر** بوت اعمالش می‌کند —
هر بوت، چون یک به‌روزرسانیِ ماژول می‌تواند دوباره روشنش کند.

آن ماژول روی یک PBXِ معمولی ابزار درستی است و در کانتینر نه: فرض می‌کند
netfilterِ ماشین مالِ خودش است، در حالی که داکر هم در همان network namespace
قاعده دارد. دو خرابیِ اندازه‌گیری‌شده روی سیستمِ زنده:

۱. **قاعدهٔ DNS داکر را پاک می‌کند** — همان چیزی که بالا توضیح داده شد.

۲. **کلاینتِ سالم را می‌بندد.** `fpbxratelimit` بعد از حدود ۱۰۰ بسته در ۳۰۰
   ثانیه — که یک نرم‌افزارِ تلفنِ فعال به آن می‌رسد — منبع را در فهرست
   `ATTACKER` می‌گذارد و بی‌صدا `DROP` می‌کند. بدتر: هر بستهٔ دورانداخته‌شده
   زمان را از نو می‌زند، پس کلاینتی که مدام تلاش می‌کند **خودش بن را زنده نگه
   می‌دارد** و هیچ‌وقت خودبه‌خود تمام نمی‌شود. نشانه‌اش «Request Timeout» است،
   نه «رمز اشتباه».

`fail2ban` جداست، دست نمی‌خورد و روشن می‌ماند — و همان چیزی را می‌بندد که
واقعاً مهم است: تلاش‌های پیاپیِ ورود با رمزِ غلط روی پورتِ رو به اینترنت.

اگر ماژول را می‌خواهی، در `pbx.env`:

```
PBX_FIREWALL=on
```

و برای اصلاحِ کانتینری که همین حالا بالاست:

```bash
docker exec freepbx fwconsole firewall disable
docker exec freepbx grep <IP> /proc/net/xt_recent/ATTACKER   # کسی بن است؟
docker exec freepbx sh -c 'echo -<IP> > /proc/net/xt_recent/ATTACKER'
```

## هشدار «۷۷ فایل دستکاری شده» — هشدار کاذب است

بعد از نصب، پنل با رنگ قرمز می‌گوید ده‌ها فایل altered شده‌اند. بررسی شد:

```
۸۰۸۴ فایل framework بررسی شد → ۲۶ خطا
۲۲ png ، ۳ zip ، ۱ gz
php / js / sh / conf / sql:  صفر
```

و اختلاف واقعی، در `amp.png`، دقیقاً **۹ بایت** است — چانک `tIME` در PNG
(تاریخ ساخت فایل) به‌علاوهٔ CRC چهاربایتی‌اش:

```
اصلی : 07d7 060e 161b 32   →  ۲۰۰۷-۰۶-۱۴
نصب‌شده: 07e9 0909 0b17 32   →  ۲۰۲۵-۰۹-۰۹
```

در `test.tar.gz` هم دقیقاً **۴ بایت**: فیلد mtime در هدر gzip، با همان تاریخ.
داده‌های تصویر و محتوای فشرده بایت‌به‌بایت یکسان‌اند.

یعنی بستهٔ دبیانی FreePBX با ابزارهای build بازتولیدپذیر ساخته شده که
timestamp تعبیه‌شده در png/zip/gz را یکدست می‌کنند، ولی فایل امضای ماژول
(`module.sig`) بر اساس تاربال دست‌نخوردهٔ بالادست امضا شده. هر فایل باینریِ
دارای timestamp علامت می‌خورد و هیچ فایل کدی نمی‌خورد.

یک فایل واقعاً غایب است — `incoming-call-no-longer-avail.sln`، یک فایل صوتی.

## چرا privileged و چرا systemd

اسکریپت رسمی با `set -e` اجرا می‌شود و چند جا `systemctl` صدا می‌زند. بدون
systemd واقعی، اولین `systemctl` نصب را وسط کار می‌ترکاند. پس کانتینر با
`/sbin/init` به‌عنوان PID 1 بالا می‌آید و همین `privileged: true` را لازم
می‌کند (نوشتن روی cgroup، و iptables برای ماژول فایروال).

یعنی این کانتینر ایزولاسیون امنیتی جدی‌ای از هاست ندارد. سرور را طوری در نظر
بگیرید که انگار FreePBX مستقیم رویش نصب است.
